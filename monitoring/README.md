# Monitoring: Prometheus, Grafana, exporters, pg_stat_statements

Live view during runs, tier by tier (proposal 4.3: "monitoring scrapes every node so each
run can be attributed tier by tier"). The run report itself does not depend on this
stack: `analysis/sampler.py` records what the report needs directly from the DB servers.

```
monitoring/
  db_setup.sql                         pg_stat_statements + rrb_monitor role (pg_monitor)
  docker-compose.yml                   Prometheus + Grafana on the monitoring host
  prometheus/prometheus.yml            scrape config (5 s): app, postgres, node exporters
  exporters/postgres_exporter_queries.yaml   WAL, waits, replication lag, log growth, checkpoints, DEFAULT partitions
  grafana/provisioning/                datasource + dashboard provider
  grafana/dashboards/rrb-overview.json dashboard "RRB benchmark" (generated by grafana/build_dashboard.py)
```

## 1. Database (both nodes)
Edit `postgresql.conf` on the primary and the replica (not ALTER SYSTEM: ShaktiDB does not
split comma lists there), restart, then run the SQL on the primary:
```
shared_preload_libraries = '<existing list>, pg_stat_statements'
pg_stat_statements.max   = 5000
pg_stat_statements.track = top
track_io_timing          = on
```
```bash
psql -d rrb -v monitor_password="'<secret>'" -f db_setup.sql
```
Run it before starting the app servers (passwd_change refuses password changes for roles
with open sessions in a database without its audit table). Keep these settings identical
in every run, including the feature on/off runs. Add `pg_wait_sampling` too if the target
ShaktiDB build has it (not in 18.6.1.0 locally).

## 2. Exporters (each machine)
node_exporter on every machine, including load generators and sdbPool nodes:
```bash
node_exporter --web.listen-address=:9100
```
postgres_exporter next to each database node:
```bash
DATA_SOURCE_NAME="postgresql://rrb_monitor:<secret>@localhost:5432/rrb?sslmode=disable" \
postgres_exporter --web.listen-address=:9187 \
  --collector.stat_statements \
  --extend.query-path=exporters/postgres_exporter_queries.yaml
```
Check the flag names with `postgres_exporter --help` for your version. If
`--extend.query-path` is gone, run the custom queries with sql_exporter; the built-in
collectors still cover pg_stat_database and pg_stat_statements.

sdbPool: commented job in `prometheus.yml`. Enable it once the sdbPool team confirms how
it exposes statistics (pgbouncer_exporter if it is PgBouncer-compatible).

## 3. Prometheus and Grafana (monitoring host)
Put the real host names into `prometheus/prometheus.yml`, then:
```bash
docker compose up -d
```
Grafana: `http://<monitoring-host>:3000`, folder RRB, dashboard **RRB benchmark**.
Without Docker, run the same Prometheus and Grafana versions as binaries with these files
(`--config.file=prometheus/prometheus.yml`; copy `grafana/provisioning` into Grafana's
provisioning directory and point the dashboard provider at `grafana/dashboards`).

## 4. Reading the dashboard
Rows follow a request: **Load and API → App pools → Database → Hosts**. The first row
where something saturates is usually the bottleneck:

| Symptom | Likely bottleneck |
|---|---|
| Requests/s flat below the target, generator CPU high (Hosts row, role=generator) | load generator, run void |
| Threads waiting for a DB connection > 0, pool timeouts | DB too slow for the pool size, or pools too small |
| Primary CPU busy ≥ 85 %, waits mostly CPU:running | primary CPU |
| Waits LWLock:WAL*, IO:WalSync, high WAL MB/s | WAL write path / disk |
| Waits Lock:* | row or table lock contention |
| Waits IPC:SyncRep | synchronous replication |
| Replication lag growing | replica cannot keep up |
| Rows in DEFAULT partitions > 0 | run without `ensure_partitions()` |

Only the local parts were tested on this machine: every custom query runs on ShaktiDB
18.6.1.0 primary and standby, `db_setup.sql` runs (twice, idempotent), and the YAML/JSON
files parse. Prometheus, Grafana and the exporters were not run here.
